## 4. `/tools/invoke`: file writes and a null factory

```bash
curl -sS -X POST http://127.0.0.1:18979/tools/invoke -H "authorization: Bearer $T" -H 'content-type: application/json' \
  -d '{"tool":"write","sessionKey":"agent:main:main","args":{"path":"x.md","content":"y"}}'
```

```
{"ok":false,"error":{"type":"not_found","message":"Tool not available: write"}}  HTTP 404
```

The file did not land: `ws/` stayed empty. `read` answers the same 404, before and after the
session exists. The cause sits in source: `/tools/invoke` resolves tools on the `http` surface,
which builds `createOpenClawTools` only, and OpenClaw builds the base coding tools (`read`,
`write`, `edit`) only for the `loopback` surface (`OC/src/gateway/tool-resolution.ts:321,468-535`).
`write` is absent from `DEFAULT_GATEWAY_HTTP_TOOL_DENY`, so `gateway.tools.allow` cannot bring it
back. Gate step 13 cannot drive the file tools through `/tools/invoke`.

## 5. Tool profiles and `tools.alsoAllow`

`tools.effective` needs a stored session. On a fresh state it fails with
`unknown session key "agent:main:main"` (exit 1). Creating an empty session starts no run:

```bash
oc gateway call sessions.create --params '{"key":"agent:main:main"}' --json --port 18979 --token "$T"
# ... "ok": true, "key": "agent:main:main", "runStarted": false ...
oc gateway call tools.effective --params '{"sessionKey":"agent:main:main"}' --json --port 18979 --token "$T"
```

The output has top-level `agentId`, `profile` and `groups`; each group has `tools[]` with `id` and,
for plugin tools, `pluginId`. `tools.profile` and `tools.alsoAllow` changed the answer with no
gateway restart (`Change will apply without restarting the gateway`). Results with the plugin
offering `memory_search` and `memory_write`:

| `tools.profile` | lumberroom tools listed | with `tools.alsoAllow: ["lumberroom"]` |
|---|---|---|
| unset (reports `full`) | memory_search, memory_write | both |
| `full` | memory_search, memory_write | both |
| `coding` | memory_search only | both |
| `messaging` | none | both |

`coding` lets `memory_search` through by its core catalog name (`OC/src/agents/tool-catalog.ts:155-160`)
and hides every other lumberroom tool. `messaging` hides all of them, and `/tools/invoke`
`memory_search` answers 404 there; with `alsoAllow` it answers 200. `tools.alsoAllow: ["memory_search"]`
also restored the tool under `messaging`. `config validate --json` returned `{"valid":true,...,"warnings":[]}`
with `alsoAllow: ["lumberroom"]` under every profile, including unset. Setup can write
`tools.alsoAllow: [..., "lumberroom"]` for `coding` and `messaging`; under `full` or unset it
changes nothing and does no harm.

## 7. `proper-lockfile` across two processes

```bash
# lock-child.mjs: lockfile.lock(target, { realpath: false, lockfilePath: target + ".lock", stale: 10000,
#   update: 2000, retries: { retries: 50, minTimeout: 100, maxTimeout: 200, factor: 1 } })
node lock-child.mjs A 2000 & sleep 0.3; node lock-child.mjs B 200 & wait
```

```
   50ms A: requesting lock
   51ms A: acquired after 1ms
  361ms B: requesting lock
 2054ms A: released
 2098ms B: acquired after 1737ms
 2301ms B: released
```

B waited and took the lock 44 ms after A let go, and the `.lock` directory was gone afterwards.
Without `retries`, the second `lock()` fails at once with `ELOCKED Lock file is already being held`,
so the fence has to pass a retry policy.

## Facts L1 and W must use

- Install: `openclaw plugins install npm-pack:<tgz> --force --accept-capabilities`. Without the flag
  and with no TTY it exits 1 after staging and installs nothing. The install sets
  `plugins.entries.<id>.enabled: true` and, for a kind `memory` plugin, `plugins.slots.memory: <id>`.
  Reinstalling keeps the entry's `hooks` and `config`. Re-enabling through
  `config set plugins.entries.<id>.enabled true` needs no second review.
- The plugin must have `plugins.entries.<id>.hooks.allowConversationAccess: true` or OpenClaw drops
  both `before_prompt_build` registrations with a diagnostic.
- `plugins inspect <id> --runtime --json` prints `PluginInspectReport` at the top level plus
  `install`. Gate paths: `.plugin.status` (`"loaded"`), `.plugin.kind` (string `"memory"`),
  `.plugin.activationReason`, `.plugin.error` (set when disabled), `.typedHooks[].name`,
  `.tools[].names`, `.policy.allowConversationAccess` (absent until configured),
  `.diagnostics[].message`. Tools and typed hooks need `--runtime`; without it memory-core showed
  none.
- memory-core reasons: `bundled (disabled by default)` with no entry and dreaming off;
  `disabled in config` when its entry says `enabled: false`; `loaded` with
  `dreaming sidecar for selected memory slot "lumberroom"` whenever dreaming is on and its entry is
  not `enabled: false`, and then it registers its own `memory_search`, `memory_get`, `intent` and a
  `before_prompt_build` hook. OpenClaw never printed `memory slot set to` in these states.
- The probe reaches the hook runner through `registerHttpRoute` with `auth: "gateway"` and
  `Authorization: Bearer <gateway token>`; no header gives 401. The plugin's `openclaw` peer is a
  symlink to the host package, so `getGlobalHookRunner()` is the gateway's runner. No gateway-method
  fallback.
- `/tools/invoke` never offers `read`, `write` or `edit` (404 `Tool not available`), so gate step 13
  must drive the guard through a probe route that calls
  `runner.runBeforeToolCall({ toolName, params }, { ...ctx, toolName })` and reads `.block` and
  `.blockReason`. `/tools/invoke` does run `before_tool_call` for tools it offers and answers 403
  `tool_call_blocked` with the hook's `blockReason` as `error.message`.
- A tool factory returning `null` makes `/tools/invoke` answer 404
  `{"ok":false,"error":{"type":"not_found","message":"Tool not available: <name>"}}`.
  `/tools/invoke` needs no stored session for `agent:main:main`.
- `tools.effective` needs a stored session: create one with
  `openclaw gateway call sessions.create --params '{"key":"agent:main:main"}' --json --port <p> --token <t>`
  (`runStarted: false`, no model turn). Then
  `openclaw gateway call tools.effective --params '{"sessionKey":"agent:main:main"}' --json --port <p> --token <t>`
  returns `{agentId, profile, groups:[{tools:[{id, pluginId?}]}]}`.
- `tools.alsoAllow` is needed for `coding` (only `memory_search` survives there) and `messaging`
  (no lumberroom tool survives). Adding the plugin id restores every lumberroom tool. It changes
  nothing and validates clean under `full` or with the profile unset.
- Gateway health: `openclaw gateway health --port <p> --token <t>` exits 0 on a running gateway and
  1 on a wrong token or a stopped gateway. `--json` adds `.plugins.loaded` and `.plugins.errors`.
- `openclaw --version` prints `OpenClaw 2026.9.6 (eb377ac)`.
- `proper-lockfile` with `realpath: false` and `lockfilePath` serialises two processes only when the
  caller passes `retries`; the default fails with `ELOCKED`.
- Gate hygiene the plan lacks: OpenClaw writes its log to `/tmp/openclaw/openclaw-<date>.log`
  whatever `OPENCLAW_STATE_DIR` says (`OC/src/infra/tmp-openclaw-dir.ts:5`); the gate should set
  `logging.file` inside its work directory. The gateway also advertised itself over Bonjour on the
  LAN and downloaded a remote model catalog at start; the gate may want
  `plugins.entries.bonjour.enabled: false` (not tried here). With `env -i` and no provider config,
  no model call happened.
